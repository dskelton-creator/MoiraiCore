Platform reference · v2.0

MoiraiCore is the local control plane for AI work.

A domain-agnostic, local-first platform that turns goals into governed agent execution, preserves outputs and organisational knowledge, and gives operators a single Mission Control interface for projects, workflows, intelligence, audit, and automation.

01

Platform overview

One operating model for planning, executing, governing, and retaining AI-assisted work.

Mission Control

Single-page dashboard for Home, Jarvis, Outputs, Goals, Agents, Projects and an expandable operational workspace. It is served locally by the same control plane.

Execution system

The Goal Engine decomposes outcomes into dependent subtasks, assigns capable agents, records state, executes work, verifies outputs and synthesizes reports.

Persistent intelligence

Vault files, outputs, agent memory, daily notes and project context are indexed in SQLite FTS5 and linked into a navigable knowledge graph.

Design principle: MoiraiCore controls the work system — plans, boundaries, quality gates, evidence and project state — while models and specialist agents execute within those constraints.

Runtime & request flow

How an operator action becomes governed, observable execution.

1 · IntentOperator creates a goal, starts a workflow, asks Jarvis, or invokes an API.
→
2 · Control planeServer authenticates, validates input, loads project context and records durable state.
→
3 · PlanGoal engine decomposes work; router selects agents; ScrumMaster applies tier and contract rules.
→
4 · ExecuteHermes, Gemini or local workers produce scoped artifacts in the project/workspace.
→
5 · GovernVerification, guardian scanning, audit/activity logging, corrections and output synthesis.

Primary runtime directories

scripts/ platform modules · dashboard/ SPA · config/ operational state · memory-vault/ retained knowledge · workspace/ generated work · projects/ customer/project isolation.

Local-first boundary

The server binds locally, data is stored under the platform root, and external services are invoked only through configured providers, outbound webhooks, or explicit intelligence integrations.

05

Agents, routing & model execution

Registry-driven specialization with Hermes as the common execution bridge.

Registry

agent_registry.py defines agent identity, strengths, trigger phrases, toolsets, memory folders and output patterns. Project-specific overrides can be persisted without rewriting built-ins.

Hermes Bridge

hermes_bridge.py builds prompt context, applies agent memory, routes by trigger, invokes Hermes CLI, records sessions and logs activity.

Model routing

model_router.py, Gemini and Ollama workers select controlled execution tiers for architecture work versus contained fixes. Tier-2 tasks routed to the antigravity engine actually execute headlessly through the Gemini API worker (gemini_worker.generate_architecture) — the same model backend the Antigravity IDE uses — writing real artifacts to .antigravity/artifacts/ and passing the scrum merge gate. The Antigravity IDE app itself has no automation surface, so the API path is the production execution route.

Agent routing is advisory, governance is authoritative. Trigger matching can propose a specialist; project-space and ScrumMaster rules decide how code reaches a customer source tree.

06

Project spaces & governed delivery

Customer/project work is isolated from MoiraiCore core and passes through a three-tier delivery model. Each project has a Slack-style Team Chat workspace: a live agent roster ("who's working on what"), @mention routing to any agent, and a real-time activity feed streamed straight from task execution.

Isolation primitives

ProjectSandbox resolves a project root, reads bounded project docs and source context, constrains outputs, and keeps customer artifacts under projects/<project>/.

Merge discipline

Workers produce artifacts; the ScrumGate checks contracts and evaluation before controlled integration to src/. This prevents ungoverned direct writes to customer code.

07

Knowledge, outputs & intelligence

Retain useful context as searchable evidence rather than disposable chat history.

Vault Index

vault_index.py indexes memory-vault files in SQLite with FTS5 full-text search, snippets, metadata and graph relationships such as wikilinks, tags, folders and agent outputs.

Unified Outputs

The Outputs surface aggregates orchestration runs, goal reports, generated reports, daily notes and agent files into one filterable browser.

Jarvis & Project Chat

Conversational intelligence with personality selection, session persistence and memory-oriented context. Each project has a scoped chat (POST /api/projects/{name}/chat) that logs user messages, Jarvis responses, agent transcripts and system events to an append-only JSONL file at projects/{name}/chat/messages.jsonl. The dashboard Team Chat tab provides a Slack-style real-time messaging UI (two-pane: live agent roster + threaded feed) with SSE streaming (GET .../chat/stream) for live updates, and supports @agent mentions that route a message to any registered agent (not just Jarvis) — with responses tagged by the target agent's identity.

Intelligence workbenches

Knowledge graph, learning/building and daily notes are specialized interfaces layered on the shared control plane.

Context precedence

For project work, project docs and source context are injected ahead of general vault context. This reduces cross-project leakage and grounds work in the correct customer space.

Security, auth & governance

Local operation does not remove the need for authentication, auditability and containment.

Authentication

auth_core.py, auth_manager.py and auth_mixin.py implement local users, password hashing, JWT access/refresh tokens, lockout protection, sessions and OAuth2 client registry support.

Audit & guardrails

Audit events, goal verification, correction records, guardian scanning and pipeline contracts create reviewable evidence around agent actions and generated outputs.

Boundaries

Auth protects non-public APIs. Project Sandbox constrains customer work. The 3-tier pipeline keeps code generation under ScrumMaster and gate control.

OpenAI OAuth capability

Local ChatGPT-account-backed inference, integrated as a model backend — not stored credentials in MoiraiCore.

Bridge

The local openai-oauth bridge runs on 127.0.0.1:10531/v1 and exposes OpenAI-compatible /v1/models, chat completions, responses and image endpoints. OAuth credentials remain on the local machine.

Hermes integration

Hermes is configured with provider custom, default model gpt-5.6-terra, and the bridge base URL. Thus MoiraiCore agent work executed through Hermes uses the bridge by default; openrouter/free remains the fallback.

Lifecycle safety: MoiraiCore's OpenAI OAuth module detects an existing listener and attaches rather than launching a duplicate bridge. Keep the bridge loopback-only; binding it to a network interface would expose requests made under the ChatGPT account.

# Hermes configuration health
hermes doctor

# Protected API requests require Bearer token
curl -s http://localhost:7878/api/auth/me \
  -H "Authorization: Bearer <token>"

Safe operating practices

  • Restart server after Python/dashboard edits; it does not auto-reload.
  • Verify port 7878 is free before startup.
  • Do not expose the OAuth bridge beyond loopback.
  • Use project spaces for customer work; do not add domain code to platform core.
  • Confirm actual API results, logs and output artifacts before declaring a goal complete.

3-Tier Pipeline Admin

Dashboard view for inspecting and switching the Tier 3 (Ollama) model, at Settings → System → 3-Tier Pipeline.

Overview

Shows three status cards (Tier 1 ScrumMaster, Tier 2 Gemini, Tier 3 Ollama), the current model name from all config sources, Ollama availability, and a list of pulled models.

Switch workflow

Enter a model name and click Pull & Switch. MoiraiCore runs ollama pull, then updates the default model name in ollama_worker.py, hermes_bridge.py and server.py. A live operation log shows each step.

EndpointMethodDescription
/api/tier3/configGETReturns current model names from all config files, Ollama availability, pulled models, and tier descriptions.
/api/tier3/switchPOSTBody {model_name, timeout?}. Pulls the model via Ollama CLI, patches all three config files, and returns step results.
Caution: The switch endpoint runs ollama pull synchronously. For large models the server can be unresponsive for several minutes. Default timeout is 900s.
